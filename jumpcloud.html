Active Directory Integrations

A feature that started as one small enhancement and became three years of work: a new design system, new capabilities, and a new way of working with engineering.

  • JumpCloud
  • Sr. Product Designer
  • 2023 to present
  • About three years

Overview

Connecting two systems without losing control of either

Active Directory Integrations is how IT admins connect Active Directory to JumpCloud for identity and access management. For each user, the admin chooses the source of truth: Active Directory, JumpCloud, or both.

The feature already existed when I joined. Over the next three years it kept coming back, each time with a bigger question than the last. I owned the design throughout, from the first small enhancement to the move to shared code ownership with frontend engineering.

The problem

To connect Active Directory to JumpCloud, an admin first had to install software on their domain controllers. For larger organisations that was a wall. Many admins could not, or would not, touch those servers, especially when a reboot was involved, and especially where legacy systems and strict change management were the norm. The people who needed the integration most were often the ones who could not even try it.

Each fix exposed a different problem. Once admins could connect, they needed to choose which system was in charge of a user. Delegated authority was meant to keep both sides in sync in real time, but it did not, and setting it up took too many steps and configurations on servers and domain controllers. That led to configuration errors. We shortened the process, but not enough. The setup itself had to move.

Four chapters

Each chapter answered the problem in front of us, and each answer showed the next one. The first three each moved the feature onto a newer design system. The fourth has concepts and designs ready, and has not shipped.

  1. 1

    2023: Getting connected

    It started as one small enhancement. I designed how an admin creates the connection for the many who could not install anything on their domain controllers. This work was built on the legacy design system.

  2. 2

    2024 to 2025: Choosing who is in charge

    Admins could now pick Active Directory, JumpCloud, or both as the authority for their users. We moved to the Stratus design system to handle the complexity on both the server side and the platform side. Real-time sync and the number of setup steps were the weak points.

  3. 3

    2026: Setup in the cloud

    Configuration moved off the servers and into the admin portal, with attribute mapping to control how user data lines up between the two systems. The feature moved to the Circuit design system, using AI tooling.

  4. 4

    Next: AI-assisted setup

    Concepts and designs are done for AI-assisted configuration. It has not shipped, so I treat it as the next question and not as a result.

Why it kept coming back

No single project here was large. Each started as a bounded enhancement and ended up exposing the next constraint. Staying with the feature meant I could design each round with the history of the last one in mind, instead of starting over every time.

One example: letting the connection work without installing on a domain controller removed the biggest wall, but in setups where Active Directory owned the passwords it only partly worked. That gap is what led to the delegation chapter. Seeing it coming was only possible because I had designed the first fix.

The move to cloud configuration was just as deliberate. Enterprise customers run offices around the world, and asking them to configure servers one site at a time does not scale. One place in the admin portal does.

From handoff to shared ownership

With the move to Circuit, the way we work changed as much as the interface. I also introduced Cursor and Storybook into the team's process.

Handoff

  • Designs reached engineering as files and specs
  • Intent could get lost between the design and the build
  • I saw the result only once it was already built

Shared ownership

  • I share my branch, and frontend integrates it into production code
  • Changes ship behind feature flags in staging
  • I run acceptance testing before release
  • The result I approve is the one customers get

Takeaways

Stay with the hard problem

A feature this complex is rarely solved in one project, and the design improves when the same person carries it from round to round.

Share the branch, not only the file

Working in the same code as engineering, with feature flags and acceptance testing, closes the gap that handoff leaves open.

Bring tools in by using them

Cursor and Storybook spread through the team because they were already part of how the work shipped.
